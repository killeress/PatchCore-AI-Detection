# AAPI / CAPI MES Report 判定

來源：客戶 `AAPI通信協議20260905.xlsx` 的「过漏检计算」與「画面检不良Code」，2026-09-07 實作。

## 站別與規則

報表與明細使用伺服器既有 `station_profile`；沒有伺服器站別時沿用 hostname 辨識。廠別仍依 `mes_report.facility` 選擇 Oracle 連線及 schema。

| 條件 | AAPI | CAPI（維持既有規則） |
|---|---|---|
| 過站 | 同玻璃、同廠別有 `1400 → 2100`，且 `TRANS_DATE > request_time` | 不查過站 |
| 不良 | `DEFT_OPER=1400`、`IF_NEWER=Y`、`TRANS_DATE > request_time` | `DEFT_OPER=1600`、`IF_NEWER=Y`、`TRANS_DATE >= request_time` |
| 判 NG | 任一不良命中獨立的 85 碼畫面清單 | 排除 PCK21，且 X/Y 皆有值 |
| 缺座標 | 仍可判 NG；座標匹配資訊不影響判定 | 不算有效不良 |
| 查無資料 | OK | OK |
| 不良排序 | `DEFT_DATE`，同時間再依 `TRANS_NBR`、`ITEM_NBR` | 維持既有排序 |

AAPI 清單保存在 `configs/aapi_mes_defect_codes.json`，包含客戶提供的 PCP02、PCZCC 描述。既有 622 碼字典仍僅提供嚴重程度等資訊，不作為 AAPI 白名單。清單檔案讀取失敗會回報查詢錯誤，不能當作全數 OK。

批次查詢彙總各玻璃的最後一次符合條件的快修過站時間，再對每筆推論檢查時間下限；這是「存在任一次過站」的判斷，不表示已建立本次檢測與快修批次的一對一關聯。多筆過站不會複製不良紀錄。

明細套用相同站別、過站及時間條件，保留清單外的不良供核對。AAPI 完整部署與差異部署均納入獨立清單。

## 待客戶釐清與目前採用方式

1. **查無資料時機**：目前照文件立即視為 OK。需確認尚未復判／尚未過站／MES 同步延遲時，是否應先標記待判，以及等待多久。
2. **重測與返修關聯**：目前只有 `request_time` 下限，沒有下一次檢測時間上限，也不要求過站與不良的 `TRANS_NBR` 相同。需確認是否要限定同一次檢測／快修交易。
3. **接收時間定義**：目前沿用既有 `request_time`，未調整 TCP 收訊流程。該值在等待 socket 資料前產生，可能早於真正收到 Testing 訊息；需確認以開始收訊、完整收訊或其他設備時間為準。
4. **過漏檢統計**：目前沿用可比對推論筆數為分母、既有 AOI OK 篩選與人工 Review 漏檢排除規則。需確認是否改為玻璃去重數、完成復判數，以及 Review 是否仍可調整漏檢分子。

## 驗證範圍

`tests/test_aapi_mes_report.py` 驗證畫面碼、座標缺失、嚴格時間邊界、多次過站、同玻璃多筆推論、查詢與明細一致、API 站別選擇，以及部署檔案納入。既有 CAPI MES 與 Review 測試用於回歸驗證。

SQL 以本機關聯資料測試替身執行，尚未連接現場 Oracle；正式環境的 WP_PNLHIST 查詢權限、索引效能及同步延遲仍需現場驗證。
